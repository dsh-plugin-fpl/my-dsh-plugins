# 架构与契约

## 当前状态

总仓库负责开发脚手架与版本组合；`dsh-core` 当前只有文档，没有运行时、可安装包或可调用接口。下面的能力边界是设计方向，需经真实应用验证后逐项落地。

## 两层职责

插件仓库拥有自己的实现、公开接口、单元测试、构建与发布说明，并能独立克隆开发。总仓库拥有插件地图、跨插件流程、联动测试和经过验证的 gitlink 组合。`.gitmodules` 是直接子模块清单，不引入另一份机器清单。

FPL 拆分遵循“公共能力 → 工坊应用 → 工作流组合”的方向。基础层不能反向依赖工坊；工坊通过公开能力接口组合。跨工坊操作由明确的组合方连接，不把业务循环依赖翻译成必选插件依赖。

## dsh-core 的规划边界

候选职责包括应用与能力注册、公共配置、身份授权适配、模型与 Agent 接入适配、资源交接协议、任务恢复接口和宿主装配。是否由 core 实现或调用宿主能力，需要逐项确认。文件库、生成引擎、渲染器和各工坊业务不默认全部装入 core。

首个实现阶段应验证“公共配置 → 模型或 Agent 接入 → 一个真实应用”，覆盖授权、任务查询和资源交接，之后再扩充。规划不构成接口承诺。

## 插件之间的公共契约

| 契约 | 提供方需要明确 |
| --- | --- |
| 能力 | 输入输出、版本、必选与可选依赖、错误语义 |
| 资源 | 所属服务、资源 ID、版本、媒体类型、来源和授权读取方式 |
| 任务 | 回执、任务 ID、进度、结果、取消、部分失败和重启后恢复 |
| 命令 | 请求 ID、版本冲突、重试与结果核对规则 |
| 事件 | 去重、顺序和恢复方式；持久状态仍是事实来源 |

正式类型、schema、Service 或 API 定义归提供方插件；调用方声明兼容版本。联合开发可以使用公开包的本地链接，正式发布不得依赖 `../其他插件/src` 或其他插件私有数据库。

资源交接传受控引用，不拼接其他插件本地文件路径。账号归属和资源访问在服务端验证，资源 ID 不是授权。组合流程持久记录所有者、输入版本、步骤回执、任务与输出引用，避免重启或超时后重复执行付费操作。

## 组合与版本

每个插件独立提交和发布，总仓库 gitlink 固定一套准确提交。接口提供方先保留兼容入口，调用方随后迁移，联动验证通过后才更新总仓库组合。独立安装需要插件自身声明依赖和版本范围，不能只依靠开发工作区恰好存在的源码。

当前没有安装包、发布流水线、生产装配或业务联动测试。后续引入这些能力时，按 [开发流程](development.md) 补充真实验证并更新本文。
