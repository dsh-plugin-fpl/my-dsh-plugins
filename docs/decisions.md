# 决策记录

## 2026-11-23：总仓库与独立插件

目的：插件可独立安装和发布，同时保留整套 Agent 开发脚手架和可还原的兼容组合。

选择 Git submodule：总仓库保存文档、工具与 gitlink，插件保存实现及正式契约。接受跨仓库无法原子提交的成本，以提供方先兼容、调用方再迁移、总仓库最后固定组合的顺序交付。

不依赖 Agent 自动跨 Git 根目录继承规则：工作区任务从总仓库启动并显式读取插件规则；插件独立规则可自足，跨插件任务再引导回工作区。

管理工具使用 Python 标准库和 Git，直接读取 .gitmodules，不维护重复清单。bootstrap 仅初始化直接子模块，版本偏移或已有修改先停止；status/check 不访问网络。通过隔离 Git 夹具测试这些行为，并以 GitHub 全新递归克隆验证交付。结构检查不替代未来的业务联动测试。

首个提交提供联合开发脚手架；具体能力在提供方仓库定义、实现并验证。

## 2026-11-23：dsh-core 第一版

将公共模型与 Agent 能力集中到独立插件，以 TypeScript 对接 Harness，以 Python 复用 FPL 的供应商、CLI 和本地模型实现。任务、配置和资源按 profile 独立持久化。后续应用通过公开 `ctx.dshCore` 接入，业务状态归各应用仓库。

核心公开契约与验收归 dsh-core；总仓库引用其文档与固定提交。第一版用真实 Harness 设置页、确定性供应商协议、五种 CLI 夹具、实际 Codex 和 FFmpeg 验证，再固定整套组合。

## 2026-11-23：Core 独立服务与 FPL 看板（当前）

用户要求 Core 生命周期脱离持续迭代中的 DSH，并直接复用已有 FPL 界面。保留现有子仓库与协议迁移成果，将业务状态、凭据和执行装配转为独立 HTTP/WS 服务；看板复用 FPL 模型目录、测试和日志页面。DSH 只提供可选的双向连接、配对设置与公共调用接口。

本条替代前述按 Harness profile 保存业务状态和由插件启动执行层的安排。服务运行包与插件 tarball 分别构建；联合启动仅负责打开两个入口。新服务使用空配置，不自动导入或改写旧 profile。接口定义、测试与迁移证据仍归 dsh-core。验证包括 HTTP 权限与持久性、DSH 断连/重连、真实看板操作、多视口、运行包独立启动以及连接层隔离安装。


## 2026-11-23：视觉与剪辑独立应用

用户选择完整迁入两个工坊的现有功能，而不是只登记旧站链接。两个仓库分别承接原业务、界面和所属素材/渲染组件；基础 Core 不依赖它们。个人品牌资源仅本机交付，独立仓库保留通用图标与无私人素材的完整加载回退。

通过 Core 公开生成参数目录避免猜测供应商尺寸；生成任务持久标记开始后再提交，未知结果不自动重放。跨工坊片段通过显式受限连接复制为目标自己的资源，避免共享私有存储和隐式相同账号假设。总仓库维护真实进程、DSH tarball 与 Chrome 组合验收，提供方保留正式接口和自身回归。

选择分开发布独立服务包和 DSH 插件，关闭 DSH 不停止任务。服务归档在外部隔离目录解包、全新依赖环境及空状态验证；子模块只固定已经推送到各仓库 main 的版本。

工作区管理测试的 README 使用固定单插件夹具，不再复制实际产品插件地图；否则新增工坊的合法文档链接会在故意只包含一个插件的夹具中被误判为失效。真实地图由实际工作区与全新 GitHub 递归克隆检查覆盖。


## 2026-11-23：六工坊与统一账号组合

按用户选择新增四个私有仓库，以 main 交付完整业务和原界面；Core 0.4 提供统一账号，已有视觉/剪辑适配到同一授权体系并保留原 owner 和任务账本。每个应用独立构建、锁定依赖、运行与发布，DSH 仅连接。正式接口由提供方维护，组合验收使用公开 CLI/HTTP/WS 与提供方明确维护的测试夹具，不导入其他仓库私有 Python 模块。

采用七进程双账号、真实资源与 FFmpeg、确定性模型/飞书、Chrome 和真实 Harness 安装测试。受保护原 FPL 文档不生成、不迁移、不改写；思绪官方包作为原文件复制并显式导入。依赖顺序为 Core、应用、父仓库 gitlinks；每个仓库分别提交到自己的 `main`，推送仍按用户授权执行。


交付复核以实际 GitHub 递归克隆和锁定安装为准，显式声明编译依赖脚本策略。思绪的内部 writing SSE 使用有界流传输，不能用缓冲 ASGITransport 代替；提供方隔离夹具支持显式分块间隔，以公开 Core 任务状态证明增量交付及断流取消。父仓库保留这些组合测试，不复制业务实现。

## 2026-11-24：开关与服务生命周期一致

用户选择开启启动、关闭停止，替代此前插件仅连接的默认值。Core 0.5 提供本机 Node 管理合同，应用各自通过公开 CLI 启停，不跨应用访问私有数据。默认退出 Harness 正常停机；manageService=false 保留常驻模式。verify_plugin_lifecycle.mjs 用当前七份 tarball、真实 Cordis 与进程、隔离账号和端口验证启停、重启和 Core 依赖级联。

## 2026-11-24：包内服务与宿主安装控制

保留独立 Python 服务的业务所有权。npm 插件携带提供方自己的生产载荷、锁文件与编译界面，以 SHA256 清单标识内容，不能发布本机路径描述、虚拟环境、数据或私人品牌资源。Core 连接层提供服务安装控制面，使服务不存在时仍可打开安装向导；只通过公开 CLI 启停、配置授权，不直接改其他插件数据库。默认安装路径与业务数据分开；已有外部服务模式继续支持。首轮仅支持 macOS，Apple Silicon 实测，Intel 仅做静态载荷检查。

账号授权由已认证 Core 浏览器批准，Host 持有独立领取证明；私有回执通过提供方 CLI 写入自己的配置，重复领取可恢复，不自动转移账号归属。工具从提供方公开 OpenAPI 白名单生成，Host 使用兼容的 schema 子集展示，执行前后仍按完整 schema 校验；文件采用有界临时文件与分块 Core 资源流。供应商付费调用在验收中用提供方公开夹具模拟，不将模拟结果表述为真实供应商验收。候选不发布；总仓库 gitlink 在相关插件提交后按用户授权更新，正式版本另行分配并按载荷摘要复验。
