# 架构与契约

## 当前能力

总仓库维护开发脚手架、插件地图、版本组合与联动验收。`fpl-core` 提供公共模型、Agent、本地模型、任务与资源服务，以及独立 FPL 看板和可选的 Harness 连接层。

## 两层职责

插件仓库拥有自己的实现、公开接口、单元测试、构建与发布说明，并能独立克隆开发。总仓库拥有插件地图、跨插件流程、联动测试和经过验证的 gitlink 组合。`.gitmodules` 是直接子模块清单，不引入另一份机器清单。

FPL 拆分遵循“公共能力 → 工坊应用 → 工作流组合”的方向。基础层不能反向依赖工坊；工坊通过公开能力接口组合。跨工坊操作由明确的组合方连接，不把业务循环依赖翻译成必选插件依赖。

## fpl-core 的职责

公共 Python 包 `fpl_core` 负责供应商与 CLI 协议、本地推理、账号、配置、会话、任务和资源持久化。桌面产品将其装配到自己的 Python 后端进程，不启动 Core 子服务；公共 React UI 与 Electron 运行库也由 Core 仓库统一维护。独立 HTTP/WS 服务保留为兼容入口。React 看板复用 FPL 的页面和组件，通过 Core 自有 API 工作。TypeScript 连接层提供 Cordis Service `ctx.dshCore`、受限应用工具、原生模型和工具回调，以及配对设置页。

兼容服务有自己的启动器和 `.runtime/core/`；托管模式随 Harness 开关正常启停，manageService=false 时独立常驻。供应商凭据由 Core 管理，Harness Credentials 仅保存可撤销配对凭据。应用 ID 在配对范围中限定，DSH 连接器通过提供方公开启动器管理进程，不持有业务数据库。首次启动为空配置，不迁入旧 profile 状态。

应用登记稳定的应用 ID，按会话提交幂等任务，通过资源 ID 交接输出。正式类型、任务语义和接入示例由 [Core API](../fpl-core/docs/api.md) 提供；FPL 拆分范围与实现顺序见 [能力盘点](../fpl-core/docs/scope.md)。

## 插件之间的公共契约

| 契约 | 提供方需要明确 |
| --- | --- |
| 能力 | 输入输出、版本、必选与可选依赖、错误语义 |
| 资源 | 所属服务、资源 ID、版本、媒体类型、来源和授权读取方式 |
| 任务 | 回执、任务 ID、进度、结果、取消、部分失败和重启后恢复 |
| 命令 | 请求 ID、版本冲突、重试与结果核对规则 |
| 事件 | 去重、顺序和恢复方式；持久状态仍是事实来源 |

正式类型、schema、Service 或 API 定义归提供方插件；调用方声明兼容版本。联合开发可以使用公开包的本地链接，正式发布不得依赖 `../其他插件/src` 或其他插件私有数据库。

资源交接传受控引用，不拼接其他插件本地文件路径。账号归属和资源访问在服务端验证，资源 ID 不是授权。组合流程持久记录所有者、输入版本、步骤回执、任务与输出引用，避免重启或超时后重复执行付费操作。

## 组合与版本

每个插件独立提交和发布，总仓库 gitlink 固定一套准确提交。接口提供方先保留兼容入口，调用方随后迁移，联动验证通过后才更新总仓库组合。独立安装需要插件自身声明依赖和版本范围，不能只依靠开发工作区恰好存在的源码。

fpl-core 分别生成独立服务运行包与 DSH 连接器 tarball。连接器安装到 Harness profile；服务可单独启动，也可由联合启动入口同时打开看板和 DSH。验收结果见 [插件验证记录](../fpl-core/docs/verification.md)。新应用加入后，按 [开发流程](development.md) 扩充组合验收。

托管安装候选中，连接器 tarball 同时携带自身独立服务的生产载荷；独立运行包仍可使用。安装控制面归 Core 连接层，安装、启停与配对通过提供方公开启动器/CLI 完成，业务数据和任务仍由独立服务持有。工坊原生工具的操作白名单与完整契约归各提供方，Core 只适配 Host schema、登记、校验和流式资源导入。安装协议见 [Core 安装文档](../fpl-core/docs/managed-setup.md)，不在总仓库复制定义。


## 独立工坊

六个工坊已通过公共 Core 库提供独立桌面入口，macOS Apple Silicon 候选随包包含 Python、生产依赖、公共 Core wheel、Electron、媒体工具和界面。源码只维护一份，安装产物按锁定版本包含运行副本；用户无需另装 Core。产品完整名称用于界面，项目导航直接进入本工坊列表。

六个工坊各自拥有 Python 业务、素材/渲染组件、数据库、后台执行和原 FPL 前端。DSH tarball 提供应用登记、工具和本机启动器连接，默认随开关管理进程。兼容服务模式下 Core 0.5 管理统一账号、可撤销的应用授权、按账号隔离的供应商凭据、任务、资源和飞书同步步骤。各应用通过公开协议接入，后端持续核验账号与授权。

应用的私人项目与业务账本由各自提供方持有；未配置时沿用自己的 `.runtime/`，配置统一存储后使用根目录的 `workshops/<稳定应用 ID>/`。旧视觉/剪辑应用为初始 Core 账号保留原 owner 投影，其余账号有独立 Core 桥接与账本。跨工坊通过 Core 签发的精确短期授权，绑定方法、路径、字节摘要、来源、目标和当前账号；原件复制到目标自有存储，不读取另一仓库数据库或文件路径。保留任务幂等、版本冲突、取消、部分失败及未知结果核对，重启不重放付费请求。

正式定义归 Core 与各应用仓库，总工作区只维护版本组合与公开 CLI/HTTP/WS 验收。原 FPL 服务、持久数据和受保护产品文档不改动。思绪官方知识包保留原文件，只有管理员显式导入才写入新库。

统一存储的定位和协调协议归 Core，数据结构与导入事务仍归提供方。来源 FPL 由自己的装配 CLI 生成公开包，协调器不访问应用私有表。每次迁移有冻结计划、停写门禁、文件校验、账号映射和持久回执；已开放新目录写入后禁止自动退回旧副本。详见 [正式存储合同](../fpl-core/docs/storage.md)。


桌面模式的数据目录与产品一起管理。全新桌面安装各自维护账号与公共设置；旧共享 Core 的账号通过显式迁移保留原 ID，并投影到各产品原所有者。导入成对冻结来源快照，保留项目、任务和资源，重加密 Core 凭据并清理旧浏览器会话；重试不混入来源后续写入，也不覆盖目标新写入。桌面中的存储页展示产品目录，不复用独立 Core 的全局搬迁控制。新桌面的跨工坊授权与 DSH 直接端点仍待组合验收，旧兼容入口继续保留。
