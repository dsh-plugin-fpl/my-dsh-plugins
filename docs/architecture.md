# 架构与契约

## 当前能力

总仓库维护开发脚手架、插件地图、版本组合与联动验收。`dsh-core` 提供公共模型、Agent、本地模型、任务与资源服务，以及独立 FPL 看板和可选的 Harness 连接层。

## 两层职责

插件仓库拥有自己的实现、公开接口、单元测试、构建与发布说明，并能独立克隆开发。总仓库拥有插件地图、跨插件流程、联动测试和经过验证的 gitlink 组合。`.gitmodules` 是直接子模块清单，不引入另一份机器清单。

FPL 拆分遵循“公共能力 → 工坊应用 → 工作流组合”的方向。基础层不能反向依赖工坊；工坊通过公开能力接口组合。跨工坊操作由明确的组合方连接，不把业务循环依赖翻译成必选插件依赖。

## dsh-core 的职责

Python 直接提供独立 HTTP/WS 服务，负责供应商与 CLI 协议、本地推理、配置、会话、任务和资源持久化。React 看板复用 FPL 的页面和组件，通过 Core 自有 API 工作。TypeScript 连接层提供 Cordis Service `ctx.dshCore`、受限应用工具、原生模型和工具回调，以及配对设置页。

服务有自己的启动器和 `.runtime/core/`；关闭 Harness 不停止服务。供应商凭据由 Core 管理，Harness Credentials 仅保存可撤销配对凭据。应用 ID 在配对范围中限定，DSH 连接器不启动执行进程，也不持有业务数据库。首次启动为空配置，不迁入旧 profile 状态。

应用登记稳定的应用 ID，按会话提交幂等任务，通过资源 ID 交接输出。正式类型、任务语义和接入示例由 [dsh-core API](../dsh-core/docs/api.md) 提供；FPL 拆分范围与实现顺序见 [能力盘点](../dsh-core/docs/scope.md)。

## 插件之间的公共契约

| 契约 | 提供方需要明确 |
| --- | --- |
| 能力 | 输入输出、版本、必选与可选依赖、错误语义 |
| 资源 | 所属服务、资源 ID、版本、媒体类型、来源和授权读取方式 |
| 任务 | 回执、任务 ID、进度、结果、取消、部分失败和重启后恢复 |
| 命令 | 请求 ID、版本冲突、重试与结果核对规则 |
| 事件 | 去重、顺序和恢复方式；持久状态仍是事实来源 |

正式类型、schema、Service 或 API 定义归提供方插件；调用方声明兼容版本。联合开发可以使用公开包的本地链接，正式发布不得依赖 `../其他插件/src` 或其他插件私有数据库。

资源交接传受控引用，不拼接其他插件本地文件路径。账号归属和资源访问在服务端验证，资源 ID 不是授权。组合流程持久记录所有者、输入版本、步骤回执、任务与输出引用，避免重启或超时后重复执行付费操作。

## 组合与版本

每个插件独立提交和发布，总仓库 gitlink 固定一套准确提交。接口提供方先保留兼容入口，调用方随后迁移，联动验证通过后才更新总仓库组合。独立安装需要插件自身声明依赖和版本范围，不能只依靠开发工作区恰好存在的源码。

dsh-core 分别生成独立服务运行包与 DSH 连接器 tarball。连接器安装到 Harness profile；服务可单独启动，也可由联合启动入口同时打开看板和 DSH。验收结果见 [插件验证记录](../dsh-core/docs/verification.md)。新应用加入后，按 [开发流程](development.md) 扩充组合验收。


## 独立工坊

`dsh-visual-workshop` 与 `dsh-video-editor` 各自拥有 Python 业务、素材/渲染组件、数据库、后台执行和原 FPL 前端。DSH tarball 仅提供应用登记与公开工具，不启动业务进程。应用的本机所有者票据与会话独立，配置、凭据和持久状态保存在自己的 `.runtime/`。

视觉生成使用 Core 0.3.1 的公开参数目录、任务回执和分块资源，供应商密钥留在 Core。未发送的取消不会提交；提交回执未知时不重放，通过显式原回执核对恢复。剪辑到视觉的片段交接使用短时邀请、双向受限连接、所有者映射及目标独立媒体复制，保留源端决策和目标幂等，不共享私有数据库或跨应用路径。

来源与正式接口归各工坊仓库；总工作区只通过公开 CLI、HTTP/WS 和安装 tarball 验证组合。旧 FPL 账号、数据与全局平台不进入新服务，通用能力由 Core 管理。
